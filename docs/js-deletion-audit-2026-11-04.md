# JS deletion audit — which JavaScript can safely be removed (2026-11-04)

Scope: all **205** files tracked under `client/js/`.
Method: authoritative provenance, not filename similarity.

## Headline result

**Delete nothing yet. 0 of 205 files are safe to remove today.**

Every file that has a compiling Rust counterpart is *still referenced* by live
JavaScript, build tooling, or tests. Removing any of them would break the client.

## Method

The earlier attempt at this audit failed because it matched Rust files to JS by
filename similarity. That is the wrong signal, and it produces false positives.

The crate carries its own authoritative provenance: **195 of 203 `.rs` modules begin
with a header naming the exact `client/js/...` file(s) they port**, e.g.

```
//!   zoom.rs      <- client/js/game/zoom.js
//!   collision.rs <- placement-collision.js, world/scaffolding.js
```

`src/lib.rs` additionally splits the crate into two explicit sets:

| Set | Count | Meaning |
|---|---|---|
| compiled modules | **119** | type-check today; in the default build |
| `unsupported_port` modules | **80** | ported but do not compile; gated behind `#[cfg(feature = "unsupported")]` |

Cross-referencing the 205 tracked JS files against those headers gives 168 JS files
with a provenance claim and 37 without.

## Verdicts

| Verdict | Count | Meaning |
|---|---|---|
| `NOT-SAFE` | **101** | cited only by gated/non-compiling Rust — the Rust side does not build, so the JS is still the working implementation |
| `NO-PORT-CLAIM` | **61** | no Rust module names this file (browser glue, entry points, tooling) |
| `CANDIDATE` | **43** | every Rust module citing it compiles |
| **safe to delete** | **0** | see below |

## Why even the 43 candidates are not deletable

A compiling Rust port is necessary but **not sufficient**. The JS must also be
superseded — nothing may still load it. I checked all 43 candidates for remaining
references across `client/*.html`, `client/js/**`, `tools/**`, `rust/build.mjs`
and `package.json`:

**43 of 43 candidates are still referenced. 0 are unreferenced.**

Highest-reference candidates:

| JS file | Remaining references |
|---|---|
| `client/js/world/blocks.js` | 96 |
| `client/js/platform/platform.js` | 76 |
| `client/js/util/zip.js` | 36 |
| `client/js/gui/i18n.js` | 35 |
| `client/js/render/models.js` | 31 |
| `client/js/game/game.js` | 25 |
| `client/js/render/entity-renderer.js` | 17 |

Examples of what still depends on them:

- `zip.js` is imported by `asset-source.js`, `render/shader-pack.js`, `tools/build.cjs`.
- `widgets.js` is imported by `gui/recipebook.js`, `screens/accounts.js`, `screens/book.js`, `screens/chat.js`.
- `mesher.js` is imported by `render/breaking.js`, `render/mesh-service.js`.
- `software.js` is used by four `tools/test-*.mjs` regression suites.

The Rust implementations exist in parallel; the JS is still the live path. This is
consistent with the crate's own documented design:

> The originals stay in place as the reference implementation and the fallback path;
> the JS glue in `client/js/wasm/` selects the WASM kernel when it is available.

## What must happen before any deletion

1. **Wire the WASM kernels in.** `client/js/wasm/` must actually load the compiled
   module and dispatch to it, replacing the JS path rather than supplementing it.
2. **Make the gated 80 compile.** Until then their JS cannot even be considered.
   `cargo check --features unsupported` currently fails.
3. **Re-run this audit after wiring.** A file becomes deletable only when its Rust
   port compiles *and* nothing references the JS any more.
4. **Run the browser regressions** (`tools/test-client-regressions.mjs`,
   `tools/test-graphics-backends-browser.mjs`) after each removal, not at the end.

## Caveats on this audit

- Reference counting uses textual matches for the basename. Dynamic imports built
  from strings, or references written with a different path shape, could be missed —
  so treat the reference counts as a **lower bound**. That makes the "do not delete"
  conclusion stronger, not weaker.
- `NO-PORT-CLAIM` (61 files) is not a deletion list either. Those are browser-bound
  layers (DOM/WebGL/WebGPU/WebSocket/WebAudio/workers) that the crate documents as
  deliberately remaining JavaScript.
- Per-file detail is reproducible from the method above; the underlying table was
  generated by cross-referencing module headers against `git ls-files 'client/js/*'`.
