# Boat walking and camera follow-up (2026-11-05)

The user confirmed chest-boat storage opens correctly. The native integration probe continues to cover Sneak+Use outside the boat and the Inventory key while riding.

Mouse input was applied between ticks without invoking Boat.onPassengerTurned. This let the rendered camera turn past ±105 degrees and get pulled back by the next tick. Entity.turn also adjusts both previous/current rotation endpoints; the client had changed only the current rotation. The shared mouse-look helper now updates both endpoints and clamps boat yaw immediately. The tick-time boat clamp reuses it without reapplying steering rotation during mouse input. Native 1.8.9 retains unrestricted boat passenger rotation; 1.12.2+ retain their native boat clamp. Pitch limits and ordinary free look are covered separately.

Walking on a floating boat remains affected by [MC-156980](https://bugs.mojang.com/browse/MC-156980). A narrow overlap can preserve the swimming pose on the client and produce its native reduced movement speed. The diagnostic probe in tools/port-1.19.4/probe-boat-walking.mjs uses a MOTD-gated disposable vanilla server, actual World/LocalPlayer collision code, native packet movement and a deliberate 0.002-block feet overlap. It records pose ticks and authoritative player corrections; it is a boundary reproduction, not a native Java-client FPS comparison.

Two local mitigation experiments were rejected before publication. Moving the player onto the interpolated boat's top produced 28/42 corrections in two repeated 160-tick cases. Flattening only the existing shallow collision contact removed slow-pose ticks but produced 123/124 corrections. The native server does not accept those altered client collision predictions reliably. Neither workaround is shipped, and the report does not claim the walking issue solved. Server code/config/worlds are untouched. The camera correction is independent of these rejected experiments.
